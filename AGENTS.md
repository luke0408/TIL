# AGENTS.md (for Codex)

This document is the operational contract for AI agents working in this repository.

## 0) Authority
- Primary source of truth: `README.md`
- If this file conflicts with `README.md`, `README.md` wins.

---

## 1) Repository Goal
- Maintain high-quality TIL notes with clear structure and consistent naming.
- Prefer small, reviewable changes over large sweeping edits.

---

## 2) Project Structure (Global)

```text
.
├── docs/                    # Main TIL documents (Docusaurus docs root)
│   ├── AI_ML/
│   ├── Backend/
│   ├── Book/
│   ├── Cloud/
│   ├── DevGeneral/
│   ├── DevOps/
│   ├── Languages/
│   ├── Networking/
│   ├── OperatingSystems/
│   └── introduction.md
├── src/                     # Docusaurus app-level UI/pages/components (site code)
├── static/                  # Static assets served as-is (images/files/favicon etc.)
├── context/                 # Codex context packs (rules/skills/commands/agents)
├── assets/
│   └── excalidraw/          # Raw drawing artifacts (not canonical notes)
├── sidebars.ts              # Docusaurus sidebar config (autogenerated)
├── docusaurus.config.ts     # Site/docs build config
├── README.md                # Repository-level writing policy (highest priority)
└── AGENTS.md                # Agent execution contract
```

Structure intent:
- Canonical learning notes live under `docs/`.
- `src/` is for site/app implementation, not primary TIL note storage.
- `static/` is for static delivery assets referenced by docs/pages.
- `context/` holds codex-usable context packs:
  - `rules/`: always-on policies
  - `skills/`: repeatable task procedures
  - `commands/`: execution command references
  - `agents/`: role-based operating guides
  Final notes should still be curated into `docs/`.
- Raw drawing/source artifacts live outside docs categories (`assets/excalidraw/`).
- Book materials are separated under `docs/Book/<book-title>/`.

### `src/` Detailed Guidance
- Purpose:
  - Holds Docusaurus application code (React pages/components/theme-level customizations).
  - Used for presentation behavior, not as the source of truth for study content.
- Typical contents:
  - `src/pages/`: custom site pages/routes
  - `src/components/`: reusable UI components
  - `src/css/`: styling overrides (e.g., `custom.css`)
- Agent rules for `src/` edits:
  - Edit only when user explicitly asks for UI/layout/theme behavior changes.
  - Avoid moving TIL markdown notes into `src/`.
  - Prefer minimal, scoped edits; do not refactor unrelated UI code.
  - If `src/` change can affect rendering/build, run `npm run build` before commit.

## 3) Core Rules (Must Follow)

### 2.1 Naming
- Folder and file names should be in **English**.
- Exception: **book titles may be in Korean**.
- Prefer lowercase + snake_case for markdown filenames.
- Respect legacy filenames unless:
  - user explicitly requests rename, or
  - rename is clearly required for consistency.

### 2.2 Note Scope
- One note = one topic.
- If a note spans multiple topics, split into multiple notes.

### 2.3 Category Policy
- Conceptual principles → `docs/DevGeneral/Principle/`
- AI/ML fundamentals → `docs/AI_ML/`
- RAG / Vector DB operation topics → `docs/AI_ML/RAG/`
- Book-specific materials → `docs/Book/<book-title>/`

### 2.4 Study vs Book Separation
- Keep study discussion notes and book content separate.
- Do not merge inferred study conclusions into book-summary notes.
- If source is study discussion, explicitly mark it in note context.

### 2.5 Excalidraw / Canvas
- `*.canvas` files are not tracked.
- Do not let raw drawing files pollute docs category structure.
- If needed, keep raw artifacts under `assets/excalidraw/` and extract final content into markdown notes.

---

## 4) Writing Conventions
- Keep notes concise but complete.
- Recommended sections:
  - `Summary`
  - `Details`
  - `Reference`
- In `Reference`, use README taxonomy:
  - `issue`: issue in this repo
  - `link`: external references
- If the note mentions previously documented concepts, add inline markdown links in the body to related local notes.

---

## 5) Commit Workflow (Strict)

### 4.1 Commit Style
- Use conventional commits:
  - `docs: ...`
  - `refactor(docs): ...`
  - `chore(config): ...`
- Keep commits small and focused.
- Avoid mixing unrelated changes.

### 4.2 Size Rule
- Keep each commit under **300 changed lines** when practical.
- If large change is needed, split into multiple commits by concern.

### 4.3 Mandatory Checks
Before commit:
```bash
git diff --numstat
git diff --cached --numstat
```

After commit:
```bash
git show --stat --oneline HEAD
```

If commit is too large or mixed:
```bash
git reset --mixed HEAD~1
# split and recommit by topic
```

---

## 6) Change Workflow (Agent Procedure)
1. Read `README.md` and this file.
2. Confirm target category/path before writing.
3. Apply minimal edits needed.
4. If links/paths changed, fix internal markdown links.
5. Validate docs build when structure/links changed:
   - `npm run build`
6. Commit in small, scoped units.

---

## 7) Safety Rules for Autonomous Edits
- Do not delete user content unless explicitly requested.
- For broad restructuring, propose plan first, then apply.
- Preserve user decisions on style/category as persistent repository policy.

---

## 8) Quick Decision Guide
- Unsure where to place a note?
  - Principle-centric → `DevGeneral/Principle`
  - Model/embedding/vector concept → `AI_ML`
  - Retrieval/indexing/Vector DB ops → `AI_ML/RAG`
  - Book material → `Book/<book-title>`
- Unsure whether to split?
  - If two independent claims can each stand alone, split.
