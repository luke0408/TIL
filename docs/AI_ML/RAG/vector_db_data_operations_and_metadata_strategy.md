# 벡터 데이터 운영

## Summary

벡터 유사도는 "얼마나 비슷한가"만 알려 준다. 실제 서비스에서는 "이 사용자가 볼 수 있는가", "최신 문서인가", "정확히 이 용어를 포함하는가" 같은 조건도 함께 맞아야 한다. 그래서 프로덕션 검색은 벡터 검색에 메타데이터 필터와 키워드 검색을 결합한다. 검색 품질은 벡터 인덱스 성능보다 이 결합 방식과 데이터 운영 방식에 더 크게 좌우된다.

이 노트는 스터디 토론 내용을 바탕으로 정리했다.

## Details

### 벡터 유사도만으로 부족한 이유

임베딩은 의미의 가까움을 잘 표현하지만, 규칙으로 정해지는 조건은 표현하지 못한다. 권한, 테넌트, 언어, 작성 날짜, 문서 유형 같은 조건은 벡터 안에 들어 있지 않다. 또 고유명사, 제품 코드, 오류 번호처럼 글자가 정확히 일치해야 하는 질의에는 임베딩이 약하다. "E1023 오류"를 검색하면 의미가 비슷한 다른 오류 문서가 더 높은 점수를 받을 수 있다.

### 하이브리드 검색

그래서 보통 세 가지를 함께 쓴다. 메타데이터 필터로 검색 범위를 제한하고, 벡터 검색으로 의미가 가까운 후보를 찾고, BM25 같은 키워드 검색으로 정확한 일치를 보완한다. 벡터 검색과 키워드 검색의 점수는 척도가 달라서 직접 더할 수 없다. 그래서 RRF(Reciprocal Rank Fusion)처럼 점수 대신 순위를 합치는 방법을 자주 쓴다. RRF는 각 검색 결과에서 문서의 순위를 `1 / (k + 순위)`로 바꿔 더한다. `k`는 보통 60을 쓴다. 두 검색에서 모두 상위에 있는 문서가 가장 높은 점수를 받는다.

```python
def rrf(rankings, k=60):
    """rankings: 문서 ID를 순위대로 담은 리스트들"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

vector_hits = ["d3", "d1", "d7"]
keyword_hits = ["d1", "d9", "d3"]
print(rrf([vector_hits, keyword_hits]))  # ['d1', 'd3', 'd9', 'd7']
```

필터를 언제 적용하는지도 결과에 영향을 준다. 사전 필터는 조건에 맞는 벡터 안에서만 검색하므로 결과가 정확하다. 하지만 조건에 맞는 데이터가 아주 적으면 ANN 인덱스가 효율적으로 동작하지 않을 수 있다. 사후 필터는 벡터 검색으로 상위 k개를 먼저 뽑고 조건을 적용한다. 빠르지만 필터 후 남는 결과가 k개보다 적거나 0개가 될 수 있다. 사용하는 벡터 DB가 어떤 방식을 지원하는지 먼저 확인해야 한다.

예를 들어 pgvector는 근사 인덱스를 쓸 때 인덱스를 먼저 탐색하고 그 다음에 `WHERE` 조건을 적용한다. 조건에 맞는 행이 전체의 10%이고 `hnsw.ef_search`가 기본값 40이면, 평균 4개 행만 남는다. 0.8.0 버전부터는 반복 인덱스 스캔을 켜서 결과가 충분할 때까지 인덱스를 더 탐색하게 할 수 있다.

```sql
SET hnsw.iterative_scan = relaxed_order;

SELECT id, title
FROM chunks
WHERE tenant_id = $1
  AND lang = 'ko'
  AND deleted_at IS NULL
ORDER BY embedding <=> $2
LIMIT 10;
```

### 메타데이터 품질

메타데이터는 세 가지 면에서 중요하다. 첫째, 검색 제어성이다. 필터로 범위를 정확히 좁힐 수 있어야 권한 밖의 문서가 노출되지 않는다. 둘째, 설명 가능성이다. 출처, 섹션, 날짜가 있어야 왜 이 문서가 나왔는지 설명하고 답변에 근거를 붙일 수 있다. 셋째, 운영 안정성이다. 문서 ID와 버전이 있어야 갱신과 삭제를 추적할 수 있다. 메타데이터가 비어 있거나 값이 일관되지 않으면 필터가 조용히 문서를 빠뜨린다.

### 운영 이슈

| 이슈 | 증상 | 대응 |
| --- | --- | --- |
| 스키마 진화 | 새 필드로 필터하면 기존 문서가 빠짐 | 필드 추가와 함께 백필 |
| 적재 일관성 | 삭제·수정된 내용이 계속 검색됨 | 문서 ID와 해시로 변경 감지, 삭제 전파 |
| 재색인 | 모델 교체 후 검색 결과가 무너짐 | 전체 재임베딩, 새 인덱스로 별칭 전환 |
| 애매한 유사도 | 관련 없는 문서로 그럴듯한 답변 | 기준값, 키워드 검색 전환, "모름" 응답 |

스키마 진화는 메타데이터 필드를 추가하거나 바꿀 때 생긴다. 새 필드를 추가하면 기존 데이터에는 값이 없으므로, 그 필드로 필터하면 기존 문서가 모두 빠진다. 필드를 추가할 때는 기존 데이터를 채우는 작업(백필)을 함께 계획해야 한다.

적재 일관성은 원본 문서와 벡터가 서로 맞는지의 문제다. 원본 문서가 수정되거나 삭제되었는데 벡터가 그대로 남으면, 이미 없는 내용이 검색되어 답변에 들어간다. 문서 ID와 내용 해시를 저장해 변경을 감지하고, 삭제도 벡터 DB까지 전달해야 한다.

> [!WARNING]
> 임베딩 모델을 바꾸면 기존 벡터를 그대로 쓸 수 없다. 차원 수가 같아도 벡터 공간이 다르므로 오류 없이 엉뚱한 결과가 나온다.

재색인은 임베딩 모델을 바꿀 때 반드시 필요하다. 모델이 다르면 벡터 공간이 다르므로 기존 벡터와 새 질의 벡터를 비교할 수 없다. 그래서 모든 문서를 다시 임베딩해야 한다. 서비스 중단을 피하려면 새 인덱스를 따로 만들고, 검증한 뒤 별칭(alias)을 새 인덱스로 바꾸는 방식을 쓴다. 청크 크기를 바꾸는 경우도 같다.

유사도가 애매한 구간에는 대체 정책이 필요하다. 가장 높은 유사도가 기준값보다 낮거나 상위 결과 사이의 점수 차이가 작으면, 검색 결과를 그대로 믿기 어렵다. 이때는 "관련 문서를 찾지 못했다"고 답하거나, 키워드 검색으로 바꾸거나, 질의를 다시 쓰는 방법이 있다. 유사도 점수 분포는 모델마다 다르므로 기준값은 실제 데이터로 측정해서 정해야 한다.

결국 핵심은 의미 기반 검색과 규칙 기반 필터를 처음부터 함께 설계하는 것이다. 인덱스 구조와 성능의 균형은 [벡터 인덱싱](./vector_db_architecture_and_indexing_hnsw_ivf_pq.md)에서 다룬다.
