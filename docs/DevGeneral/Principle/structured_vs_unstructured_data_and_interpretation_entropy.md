# 해석 엔트로피

## Summary

해석 엔트로피는 데이터 하나를 읽을 때 가능한 해석이 얼마나 많은지를 나타내는 말이다. 정보 이론의 엔트로피가 불확실성의 크기를 뜻하는 데서 빌려 왔다. 스터디에서 정형 데이터와 비정형 데이터의 차이를 설명하려고 쓴 용어이며, 표준 학술 용어는 아니다. 이 관점에서 정형 데이터의 핵심 가치는 표 형태라는 형식이 아니라 해석의 불확실성을 낮추는 데 있다.

이 노트는 스터디 토론 내용을 바탕으로 정리했다.

## Details

### 정형화가 줄이는 것

정형 데이터는 스키마가 필드 이름, 타입, 단위, 허용 값을 미리 정한다. 예를 들어 `due_date` 필드에 `2026-02-17`이 들어 있으면 사람과 시스템 모두 같은 날짜로 읽는다. 반면 메모에 "다음 주 화요일쯤"이라고 쓰여 있으면, 기준 날짜가 언제인지와 "쯤"이 얼마나 넓은지에 따라 해석이 달라진다. 정형화는 이런 해석 규칙을 데이터를 쓰는 시점에 고정한다. 그래서 읽는 쪽은 해석할 필요 없이 바로 사용할 수 있다.

해석 엔트로피가 낮으면 후속 처리 비용이 줄어든다. 값을 검증하고, 집계하고, 다른 데이터와 조인하는 작업을 규칙대로 자동화할 수 있다. 반대로 해석 엔트로피가 높은 데이터는 사용하기 전에 파싱, 추출, 분류 같은 해석 단계를 거쳐야 한다. 이 단계는 비용이 들고, 사람마다 또는 시스템마다 결과가 다를 수 있다.

| 구분 | 정형 데이터 | 비정형 데이터 |
| --- | --- | --- |
| 예 | DB 테이블, 정해진 필드의 JSON | 메모, 문서, 이미지, 대화 기록 |
| 해석 규칙 | 쓸 때 스키마로 고정 | 읽을 때마다 해석 |
| 해석 엔트로피 | 낮음 | 높음 |
| 자동화 | 검증, 집계, 조인이 쉬움 | 파싱, 추출, 분류가 먼저 필요 |
| 약점 | 예외와 변화에 약함 | 처리 비용과 결과 편차 |

### 과도한 정형화의 비용

정형화가 항상 좋은 것은 아니다. 스키마가 너무 엄격하면 현실 데이터의 다양성을 담지 못한다. 미리 정한 선택지에 맞지 않는 값은 "기타"로 뭉뚱그려지거나, 가장 비슷한 잘못된 값으로 억지로 들어간다. 이 경우 해석은 하나로 정해지지만 그 해석이 틀린 것이다. 즉 해석 엔트로피를 줄이는 대신 정보를 잃는다.

### 혼합 전략

그래서 실무에서는 혼합 전략이 유효하다. 자주 조회하고, 검증해야 하고, 다른 데이터와 연결하는 핵심 필드는 정형 스키마로 유지한다. 형태가 자주 바뀌거나 예외가 많은 부분은 JSON 컬럼이나 원문 텍스트로 유연하게 보관한다. 이렇게 하면 핵심 데이터의 해석은 고정하면서 원래 정보도 잃지 않는다.

```sql
CREATE TABLE tasks (
  id       bigserial PRIMARY KEY,
  title    text NOT NULL,
  status   text NOT NULL CHECK (status IN ('todo', 'doing', 'done')),  -- 해석을 고정
  due_date date,                                                       -- 날짜 형식 고정
  extra    jsonb NOT NULL DEFAULT '{}',  -- 팀마다 다른 부가 정보
  note     text                          -- 원문 그대로 보관
);
```

위 테이블에서 `status`와 `due_date`는 값과 형식이 고정되어 있어 누가 읽어도 의미가 같다. 반면 `extra`와 `note`는 형식을 강제하지 않는다. 자주 쓰이는 `extra` 키가 생기면 그때 정식 컬럼으로 옮기면 된다.

### 임베딩과의 관계

비정형 데이터도 의미 기반 해석이 필요할 때가 있다. [임베딩 벡터](../../AI_ML/embedding_vector_basics_dense_l2_cosine_similarity.md)는 텍스트의 의미를 벡터로 바꿔서, 스키마로 정형화하지 않고도 "비슷한 내용인가"를 비교할 수 있게 한다. 다만 임베딩은 의미의 가까움만 다루므로 권한이나 날짜처럼 정확해야 하는 조건은 여전히 정형 필드가 맡아야 한다. 이 두 방식을 함께 쓰는 방법은 [벡터 데이터 운영](../../AI_ML/RAG/vector_db_data_operations_and_metadata_strategy.md)에서 다룬다.
